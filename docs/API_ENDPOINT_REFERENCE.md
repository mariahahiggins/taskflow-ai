# TaskFlow AI — API Endpoint Reference

**Backend:** FastAPI  
**Frontend:** Streamlit  
**Database:** SQLite

## 1. Overview

Streamlit sends HTTP requests to FastAPI, which handles employee/task database operations and invokes the workload and fairness calculations. The examples below document the currently implemented employee, task, and workload interfaces. The AI endpoints are planned and must be confirmed when implemented.

## 2. Employee Endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/employees` | List employees |
| GET | `/employees/{id}` | Get one employee |
| POST | `/employees` | Add an employee |
| PUT | `/employees/{id}` | Update an employee |

**Employee response object** (also an item in `GET /employees`):

```json
{
  "employee_id": 1,
  "name": "Sarah",
  "available_hours": 40,
  "experience_level": "Mid"
}
```

Employee IDs are generated by the database. The `experience_level` values are `Junior`, `Mid`, and `Senior`. For create requests, omit `employee_id`. The existing PUT endpoint updates the employee's editable fields.

## 3. Task Endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/tasks` | List tasks |
| GET | `/tasks/{id}` | Get one task |
| POST | `/tasks` | Create a task |
| PUT | `/tasks/{id}` | Update task details, assignment, or status |

**Task response object** (also an item in `GET /tasks`):

```json
{
  "task_id": 1,
  "title": "Prepare report",
  "estimated_hours": 10,
  "deadline": "2026-11-20",
  "priority": "High",
  "difficulty": "Medium",
  "status": "Active",
  "employee_id": 1
}
```

New tasks default to `Active`. Tasks may be unassigned (`employee_id: null`). Completed tasks do not contribute to outstanding workload calculations. The PUT endpoint can change assignment and completion status. Create requests omit `task_id`.

## 4. Workload Endpoints

| Method | Endpoint | Purpose | Calculation function |
|---|---|---|---|
| GET | `/employees/{id}/workload` | Individual workload summary | `get_employee_workload_summary()` |
| GET | `/workloads` | Team totals, employee summaries, fairness, and deadlines | `get_team_workload_summary()` |

### 4.1 Individual employee workload response

The following example illustrates the **field names and types**, not a live database result. Numbers depend on current tasks and the date of the request.

```json
{
  "employee_id": 1,
  "name": "Sarah",
  "experience_level": "Mid",
  "available_hours": 40,
  "outstanding_hours": 18,
  "active_task_count": 2,
  "overdue_task_count": 0,
  "within_1_week_count": 1,
  "week_2_count": 1,
  "after_2_weeks_count": 0,
  "one_week_utilization": 25.0,
  "two_week_utilization": 22.5,
  "deadline_conflicts": []
}
```

- `outstanding_hours`: sum of estimated hours for active tasks assigned to this employee.
- `active_task_count`: number of active assigned tasks.
- `overdue_task_count`: active tasks with deadlines before today.
- `within_1_week_count`: active tasks due today through seven days from today.
- `week_2_count`: active tasks due eight through fourteen days from today.
- `after_2_weeks_count`: active tasks due more than fourteen days from today.
- `one_week_utilization`, `two_week_utilization`: percentage of available working hours needed for active tasks due by each horizon, including overdue tasks. May be `null` if capacity is zero.
- `deadline_conflicts`: list of overdue or insufficient-capacity deadline warnings.

**Deadline conflict object** (illustrative):

```json
{
  "deadline": "2026-11-12",
  "required_hours": 20,
  "available_hours": 16,
  "shortfall_hours": 4,
  "type": "capacity"
}
```

`type` is `capacity` or `overdue`. An overdue conflict has `available_hours: 0` and uses the overdue task's estimated hours as `required_hours` and `shortfall_hours`. A capacity conflict uses cumulative active hours due on or before the deadline, compared with working hours available through that deadline.

### 4.2 Team workload response

The example below shows the **response structure**. Empty collections are placeholders, not representative live results. The `employees` array contains individual workload objects with all fields documented above. The `upcoming_deadlines` array contains full active task records (as in the task response), sorted by deadline.

```json
{
  "total_employees": 3,
  "active_tasks": 5,
  "unassigned_tasks": 1,
  "outstanding_hours": 46,
  "overdue_tasks": 0,
  "employees_with_conflicts": 0,
  "total_deadline_conflicts": 0,
  "employees": [],
  "fairness": {
    "one_week_utilization_spread": 0.0,
    "two_week_utilization_spread": 0.0,
    "high_priority_tasks": {
      "1": { "count": 0, "hours": 0 }
    },
    "high_priority_count_spread": 0,
    "high_priority_hours_spread": 0,
    "difficult_tasks": {
      "1": { "count": 0, "hours": 0 }
    },
    "difficult_count_spread": 0,
    "difficult_hours_spread": 0
  },
  "upcoming_deadlines": []
}
```

**Team totals:**

- `total_employees`: number of employee records.
- `active_tasks`: active tasks assigned to a known employee; **does not include unassigned tasks**.
- `unassigned_tasks`: active tasks with `employee_id: null`.
- `outstanding_hours`: sum of assigned employees' outstanding hours.
- `overdue_tasks`: overdue active tasks assigned to employees; unassigned overdue tasks are not included in this total.
- `employees_with_conflicts`: employees with one or more deadline conflicts.
- `total_deadline_conflicts`: sum of all individual deadline conflict entries.
- `employees`: array of individual employee workload summaries.
- `upcoming_deadlines`: all active tasks, including overdue and unassigned tasks, ordered by earliest deadline first (despite the name).

**Fairness fields:**

- `one_week_utilization_spread`, `two_week_utilization_spread`: highest minus lowest non-null employee utilization percentage; `null` if fewer than two employees have a valid percentage.
- `high_priority_tasks`: per-employee counts and estimated hours of assigned, active `High` priority tasks.
- `difficult_tasks`: per-employee counts and estimated hours of assigned, active `Hard` difficulty tasks.
- `high_priority_count_spread`, `high_priority_hours_spread`, `difficult_count_spread`, `difficult_hours_spread`: maximum minus minimum values across employees; `null` if fewer than two employees are present.
- Employee IDs are integer keys in Python dictionaries, but appear as **string keys in JSON** (for example, `"1"`).

### 4.3 Calculation rules and limitations

- Only active tasks contribute to outstanding hours, utilization, deadline grouping, and fairness task counts.
- Task estimates are not automatically reduced as work progresses. Update estimated hours if remaining effort changes.
- Deadline groups are mutually exclusive; utilization windows are cumulative.
- Capacity uses Monday–Friday working days, with weekly availability divided evenly across five days. This is an approximate planning model, not an employee-specific calendar.
- Deadline conflict checks include overdue unfinished work in cumulative demand for upcoming deadlines.
- The team `upcoming_deadlines` field is not limited to future dates and includes unassigned active tasks.

## 5. Planned AI Endpoints

These are **proposed**, not confirmed as implemented. Final request/response contracts will be documented after the AI integration is available.

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/recommendations` | Generate AI assignment/reassignment suggestions |

AI recommendations should be checked against workload, deadline, and fairness constraints, and must not change task assignments until manager approval.

## 6. Frontend Integration Notes

- Fetch `GET /employees` and `GET /tasks` to populate forms and lists.
- Fetch `GET /workloads` for team dashboard metrics, fairness displays, employee workload cards, and deadline warnings.
- Fetch `GET /employees/{id}/workload` for a selected employee's detailed view.
- Display `active_tasks` as **assigned active tasks**, or combine it with `unassigned_tasks` when a total active-task count is needed.
- Handle nullable utilization and spread fields in the UI.
- Consult the FastAPI `/docs` page for the exact current Pydantic request schemas, HTTP response codes, and validation errors; these may evolve when workload response models are added.
